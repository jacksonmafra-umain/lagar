# Tjänster implementation plan

**Goal:** turn the Tjänster tab into a catalogue of public services, each linked to the norms it is based on, from an official, curated and verified source list.

**Architecture:** a curated list (`collector/data/services.json`) feeds a `services` collector that checks every official page and writes `corpus/services/`; the audit validates `based_on`; the API builder adds the `service` layer, `service/catalog.json` and `service/by-norm/index.json`; the app reads the catalogue once and filters on the device.

**Spec:** [`docs/specs/2026-11-13-tjanster-design.md`](../specs/2026-11-13-tjanster-design.md). Read it before any task; it holds the field names, the vocabularies and the decisions.

**Granularity:** one task below is one labelled GitHub issue and one pull request, assigned to the owner and merged into `main`. When a task is picked up, its implementer writes the step-by-step plan for it (test first, micro commits) inside the PR; this document fixes the order, the boundaries and the interfaces between tasks.

## Global constraints

- Everything in English except legal text, service titles and lead paragraphs as published, and Swedish UI strings.
- Collectors: `python3 -I`, stdlib first, rate at least 1 s, `robots.txt` honoured, project User-Agent, resumable and idempotent; a blocked page is a recorded gap, never bypassed.
- `based_on` is curated by hand and never inferred by a model.
- API changes are additive within v1: existing files keep their shape; new `meta` fields are present on every document, `null` where they do not apply.
- App strings in Compose resources (`values/` English, `values-sv/` Swedish); no hardcoded user-facing text; no machine translation.
- No accounts, no BankID, nothing filled in inside lagar.
- Conventional Commits, micro commits, explicit `git add` paths.

## Review focus

Conditions no single task's tests would catch by default, each pinned to the task that owns it:

1. A `based_on` id that points to a repealed norm: the audit accepts it, the detail screen shows the norm with the repealed treatment (task 2, task 9).
2. A listed page that now redirects to another host or returns 404: the collector keeps the last good corpus file, marks it in the manifest and reports it, and never writes the redirect target as the source (task 3).
3. A kommun selected whose website is missing from `kommuner.json`: template services show without the kommun link, not a broken button (task 13).
4. Service titles in the English UI: they stay Swedish; only chrome is translated (task 9, task 14).
5. A norm that has no services: the reader shows no empty "Tjänster" section (task 10).

## Phase 0: sources

### Task 1: Spike: confirm the service sources

Labels: `type: chore`, `area: collector`, `source: agency`

- Check whether the Single Digital Gateway link repository API returns Sweden's procedure links without a key, and what fields it gives (URL, title, procedure code).
- Read `robots.txt` for every seed host (skatteverket.se, forsakringskassan.se, csn.se, transportstyrelsen.se, migrationsverket.se, arbetsformedlingen.se, polisen.se, verksamt.se, 1177.se) and record which service pages may be fetched.
- Draft the seed list of about 60 services with `based_on`, taken from each page's own legal references where it gives them.

Done when: a note in the PR lists each host's verdict, the API finding and the draft list; any host that forbids automation is added as a gap to `collector/data/agencies.json`. No collector code.

## Phase 1: schema and corpus

### Task 2: `public_service` type, fields and audit check

Labels: `type: feature`, `area: corpus`

- Files: `collector/lagar/vocabulary.py`, `collector/lagar/schema.py`, `collector/lagar/audit.py`, `docs/schema/frontmatter.schema.json`, `docs/api.md` (vocabulary table, `meta` fields), `collector/tests/`.
- Add the type `public_service` (layer `service`, folder `services/`), the fields `based_on`, `audience`, `topics`, `channels`, `service_url`, `issuer_org_number`, `scope`, `template` with the vocabularies from the spec.
- Audit: `based_on` non-empty for `public_service` and every id present in the corpus; a missing id is a schema error.
- Tests: a valid service passes; an empty `based_on`, an unknown id, an unknown topic and a template service with a `municipality_code` each fail with their own message; a `based_on` id of a repealed norm passes.

Produces: the field names and vocabularies that tasks 3 to 13 use.

## Phase 2: collector

### Task 3: `services` collector and curated list

Labels: `type: feature`, `area: collector`, `source: agency`

- Files: `collector/lagar/services.py`, `collector/collect.py` (subcommand `services`), `collector/data/services.json`, `collector/README.md`, `CLAUDE.md` (commands), `collector/tests/test_services.py` with saved pages as fixtures.
- Command: `python3 -I collector/collect.py services [--slug S ...] [--limit N] [--report FILE]`. Reads the list, fetches each `source` page, extracts title and lead paragraph per host, writes `corpus/services/service-<slug>.md` and `sources/services-manifest.json` (status, final URL, `Last-Modified`, SHA-256, `fetched_at`). State in `collector/data/services-state.json`.
- A 404, a redirect to another host or a page that robots forbids keeps the previous corpus file, is marked in the manifest and appears in the report.
- Commit the seed list from task 1 and the corpus it produces (`data(services):`).

Consumes: task 2's schema. Produces: `corpus/services/` and the manifest.

### Task 4: Weekly `Sync services` workflow and reports

Labels: `type: chore`, `area: ci`, `area: collector`

- Files: `.github/workflows/sync-services.yml` (weekly, same shape as `sync-so.yml`, merging through `.github/scripts/merge-sync-pr.sh`), `collector/lagar/corpusstats.py` and `collector/lagar/progress.py` (the service layer in `STATISTICS.md` and `PROGRESS.md`, with moved and dead pages counted), `collector/data/targets.json`.
- Done when: a manual dispatch opens and merges a sync PR, and the reports show the service count and the dead links.

## Phase 3: API

### Task 5: Service layer, catalogue and reverse index

Labels: `type: feature`, `area: api`

- Files: `api/build.py`, `docs/api.md`, `docs/api/examples/service/`, `api/tests/`.
- Build the `service` layer listings and `docs/service-<slug>.json` with the new `meta` fields (`null` on every other type), `service/catalog.json` and `service/by-norm/index.json` exactly as the spec lists their fields.
- Tests: every `based_on` entry in the catalogue resolves to `{id, title, type, layer}`; `by-norm` has a key only for norms with at least one service; existing example files are unchanged apart from the added `meta` keys.

Produces: the JSON shapes tasks 7 to 12 read.

### Task 6: Services in search and in the MCP server

Labels: `type: feature`, `area: api`

- Files: `api/searchindex.py` (a `service` group with its budget), `mcp/` (`list_layers` and `search_laws` cover the layer; `get_document` returns services), tests in both.

## Phase 5: region and kommun

### Task 12: Kommun and region template services

Labels: `type: data`, `area: collector`, `source: kommun`

- Add the template services from the spec to `services.json` (bygglov, försörjningsstöd, förskola, hemtjänst, parkeringstillstånd, avfallshämtning; healthcare via 1177, färdtjänst), with `template: true`, their `scope` and `based_on`.
- The source page of a template is the national guidance page that describes the obligation (for example Boverket for bygglov), not a kommun page.

### Task 13: Kommun link on template services

Labels: `type: feature`, `area: app`

- Ship the kommun websites from `collector/data/kommuner.json` with the app or through the API (decide in the PR; prefer the app's existing geo file if it already carries them), and show "Hos <kommun>" on template services; no button when the website is missing.

## Phase 6: language and docs

### Task 14: Strings review and docs

Labels: `type: docs`, `area: app`

- Files: `values/strings.xml`, `values-sv/strings.xml`, `docs/i18n.md` (topic and audience glossary), `docs/screens.md` (Tjänster rows to done), `docs/architecture.md` (layer 9 and the tab diagram say services, not notices), `docs/replicate/PROMPT.md` and its pin, `docs/roadmap.md`.
- Done when: every service string exists in both locales, a native Swedish read-through is noted in the PR, and the replication prompt test passes.

## Order

1 → 2 → 3 → 4, and 5 after 3. 6 after 5. App tasks 7 → 8 → 9, then 10 and 11 in either order. 12 needs 3; 13 needs 8 and 12. 14 last. Tasks 4, 6, 10, 11 and 12 can run in parallel once their inputs are merged.
